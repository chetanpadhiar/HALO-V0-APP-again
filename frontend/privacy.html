HALO

Contextual Email Trust & Forensic Intelligence

PRIVACY POLICY

Last updated: September 15, 2026
This policy describes HALO V0 as it is actually implemented today. Where a control, retention rule, or workflow does not yet exist in the product, this policy says so plainly rather than describing something HALO does not yet do.

1. Overview

HALO is a contextual email trust and forensic intelligence tool built for students and educational institutions. It analyzes email messages a user chooses to connect and produces a trust assessment intended to help the user recognize phishing, impersonation, and other suspicious messages. HALO also offers a Demo Mode that uses synthetic, clearly labeled example data and makes no network requests to any mail provider.

This policy applies to anyone who uses HALO, including students who connect a personal or institutional Gmail account and institution administrators who review analysis and campaign data for their organization.

2. Information We Access

If a user chooses to connect a Google account, HALO requests read-only access to that account's Gmail messages, together with the user's basic Google profile (name and email address) needed to sign them in. With that access, HALO may read:

  • Message headers (sender, reply-to, routing/authentication headers such as SPF, DKIM, and DMARC results)
  • Subject lines and message body content, where needed to analyze the message
  • Links and URLs contained in a message
  • Basic message metadata, such as when a message was received

HALO does not request permission to send, delete, or modify email, and does not request access to Google Drive, Contacts, Calendar, or any other Google service beyond the Gmail read-only scope and basic sign-in profile described above.

A user who chooses Demo Mode instead of connecting a Google account never has any of their real email data accessed, and no Google account is contacted.

3. How We Use Information

Information read from a connected mailbox is used to identify potentially malicious or threatening email and to provide the security analysis that is HALO's purpose. In producing that analysis, HALO may derive:

  • A security classification and trust score for each analyzed message
  • Risk indicators and plain-language reasons for that classification
  • Behavioral and contextual signals, such as whether a sender has been seen before
  • Campaign relationships, where multiple messages appear to share a common domain or sending infrastructure
  • Infrastructure intelligence about the network the message appears to have been sent from

Infrastructure intelligence reflects observed network origin only. HALO does not claim, and this analysis cannot determine, the physical location of the person or system that actually sent a message — a relay, proxy, or compromised account can change the observed network origin without changing who is really behind a message. HALO also does not guarantee that it will detect every malicious or threatening email; it is a decision-support tool, not a guarantee of safety.

For institution accounts, aggregated analysis (such as campaign and infrastructure summaries) may be shown to that institution's administrators to help them understand threats affecting their students. Institution views are built to avoid unnecessarily exposing individual students' private message content or identities beyond what is needed for that purpose.

4. Gmail and Google API Access

HALO's use and transfer of information received from Google APIs adheres to the Google API Services User Data Policy, including the Limited Use requirements. Gmail data is used only to provide and improve the security analysis features described in this policy — never for serving advertisements, never sold, and never used to build user profiles for any purpose unrelated to that analysis.

We have not represented, and do not represent here, that HALO has completed Google's formal OAuth app verification or security assessment process. Google may require that process before or as a condition of production access to the Gmail scope described above; this policy is part of that process, not a claim that it has already concluded.

5. Security

HALO applies the following controls, as actually implemented in the product today:

  • Encrypted token storage: OAuth access and refresh tokens are encrypted at rest (AES-256-GCM) before being stored, using a server-side encryption key that is never exposed to the frontend.
  • Authenticated sessions: after sign-in, HALO issues a server-side session token with a limited lifetime; every request that reads or changes data is checked against that session.
  • Role separation: a user's role (student or institution) is fixed at first sign-in based on their authenticated email and cannot be changed by anything the client sends afterward.
  • Access control on data: a student's own message analysis is only readable by that student; institution-level views are limited to users authenticated with the institution role.
  • Audit logging: sign-in and authorization events are recorded with their outcome (allowed or denied) for security review.

No security control eliminates all risk. We describe these controls accurately rather than claiming a level of protection beyond what is implemented.

6. Data Storage and Retention

HALO stores account, session, and email-analysis data in a PostgreSQL database operated for this service. Encrypted OAuth tokens, message analysis results, and derived signals described in Section 3 are retained in that database to provide the ongoing dashboard and campaign features of the product.

HALO does not currently enforce an automatic data-deletion or retention-expiry schedule. We are stating this plainly rather than describing a retention period that is not yet implemented. If this changes, this policy will be updated to reflect the actual behavior of the product.

7. Data Sharing

HALO does not sell personal information, and does not share Gmail data with third parties for their own independent purposes. Data is shared only:

  • Between the parts of HALO's own infrastructure needed to operate the service (for example, sending message content to HALO's own analysis service to produce a trust score) — see Section 9 for the specific providers involved;
  • With an institution's own administrators, limited to the aggregated/analysis data described in Section 3, for students associated with that institution;
  • Where required by law, or to investigate a security incident affecting the service itself.

HALO does not use Gmail data for advertising, and does not permit any advertiser to access it.

8. Your Choices and Controls

  • Connecting a Google account is optional — HALO's Demo Mode is available without connecting any real mailbox.
  • You can revoke HALO's access to your Google account at any time from your Google Account's Security > Third-party access settings. Revoking access stops HALO from reading further Gmail data; it does not by itself delete analysis HALO has already stored (see Section 6).
  • You can request deletion of your HALO account data using the contact method in Section 12. HALO does not yet have an automated self-service deletion workflow, so this is currently handled as a manual request rather than an instant, guaranteed process.

9. Third-Party Services

HALO's production deployment actually relies on the following third-party services:

  • Google / Gmail API: used for sign-in and, where a user connects their account, read-only mailbox access as described above.
  • Vercel: hosts HALO's frontend (the pages you are using right now).
  • Render: hosts HALO's backend API and its email-analysis service.
  • PostgreSQL (via Render): the database described in Section 6.

We do not use any analytics, advertising, or tracking service beyond what is listed above.

10. Student and Institution Use

HALO is designed for use by students and by staff at educational institutions. A user's role and institution are derived automatically from their authenticated email address at first sign-in, not asserted by the user. Institution administrators can see aggregated threat and campaign information for their institution's students, built to limit exposure of individual students' private message content beyond what that aggregated view requires, as described in Section 3.

If you are a student under the age where your jurisdiction requires parental or institutional consent for a service like this, please use HALO only in the way your institution has authorized (for example, as part of an institution-provided account), and direct any questions to your institution before connecting a personal account.
